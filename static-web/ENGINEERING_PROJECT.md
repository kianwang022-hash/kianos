# KianOS Engineering Project

Status: CURRENT ENTRY CONTRACT  
Role: bootstrap source for the dedicated ChatGPT **KianOS Engineering** Project.

This file does **not** own engineering truth, website status, task queues, acceptance state, learner progress, or product strategy.

Its only job is to make a fresh Engineering Chat enter the existing KianOS owner chain correctly and cheaply.

---

## 1｜Purpose

Use this Project for:

- KianOS website / UI defects;
- Home / navigation / interaction friction;
- runtime / private control / checkpoint / Chat↔Website transport;
- performance / responsiveness;
- Astro / local Current runtime;
- browser QA / CI / regression;
- bounded engineering changes across subject surfaces.

Do not use this Project for:

- deciding what Kian should study now;
- Xizong / English / Politics learning discussion;
- cross-subject allocation or exam strategy;
- Steward / Review work;
- medical / English / Politics Content construction unless the engineering defect genuinely requires the exact Content owner.

Those remain with the learner Projects and their own owners.

---

## 2｜Fresh-chat bootstrap

A fresh Engineering Chat should normally start:

```text
main@HEAD
→ AGENTS.md
→ static-web/CURRENT.md
→ exact affected owner
→ work
```

Read `SYSTEM_CONTRACT.md` only when the task crosses shared Engineering capability/boundary.

Read Presentation / subject / Content owners only when the requested defect genuinely depends on them.

Target: roughly 2–3 precise reads before effective work.

Do not reconstruct Current truth from old Chat history, screenshots, stale branches or remembered PR state.

---

## 3｜Operating rule

Classify the request first.

Typical Engineering intents:

```text
“Home 回去很卡”
→ concrete learner-visible performance defect

“政治页面这个按钮不对”
→ exact Politics surface defect

“Chat 安排没有进网页”
→ shared/private-control transport defect

“这个页面看起来挤”
→ UI / presentation defect

“网站整体做到哪了”
→ CONTROL: read root CURRENT → static-web CURRENT
```

Then:

```text
read current owner
→ reproduce / measure
→ identify smallest responsible owner
→ change the smallest write-set
→ targeted proof
→ representative browser proof when learner-facing
→ Human Gate when material visual/product behavior changed
→ stop
```

---

## 4｜Gate 5 discipline

Website broad construction is frozen.

A real defect may reopen only the smallest responsible owner.

Do not respond to friction by starting a new architecture program, universal runtime, second packet system, second Home, second learner-state model, or broad cross-subject rewrite unless current evidence proves the existing owner model cannot represent the problem.

Default:

```text
concrete friction
→ measure first
→ narrow repair
→ remeasure
```

For performance complaints, prefer a read-only friction/performance probe before architectural optimization.

---

## 5｜Current-first and branch discipline

For ongoing engineering work:

- read the latest exact ref before acting;
- if a branch / PR is active, use its current head, not old Chat narration;
- do not continue a historical prototype merely because it still exists;
- `main` advancing for unrelated work is not itself a blocker;
- reconcile only on real write-set / authority overlap;
- never force over concurrent work.

Prototype branches are evidence unless Current explicitly promotes them.

---

## 6｜Acceptance boundaries

Keep distinct:

```text
Artifact Truth
Acceptance Truth
Learner Truth
Performance / friction evidence
```

A green CI run does not prove the page feels fast.

A synthetic browser proof does not replace real Mac learner acceptance when the complaint is real-use responsiveness.

A visual change requires representative real-browser proof and Kian Human Gate when material.

---

## 7｜Progress reporting

Keep Engineering complexity in the backend.

Normal updates to Kian should answer:

```text
现在在哪
发现了什么真实问题
已经修了什么
还剩什么 blocker
下一步
是否需要 Kian 看 / 决定
```

Do not dump branch archaeology, CI logs, implementation trivia or long SHA lists unless they materially affect the decision.

---

## 8｜Stop rule

Stop when the requested real effect is proven.

Do not keep polishing because more engineering work is possible.

The Engineering Project is a repair / implementation workspace, not a sixth learner-facing exam role and not a new Personal OS control center.
